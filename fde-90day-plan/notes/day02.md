## 1. 跑起来

```bash
python week1/day2_tools.py          # 假数据，先看懂闭环

```

`day2_tools_live.py` 是交互式的，跑起来后直接输入问题：

| 输入 | 作用 |
|---|---|
| 任意问题 | 走完整两轮闭环（天气类会触发工具，非天气类模型会直接回答） |
| `clear` | 清空对话历史重新开始 |
| `q` / `退出` | 退出程序 |

可以连着追问（比如先问"成都天气怎么样"，再问"那上海呢"），体会历史是怎么带上的。

## 2. 核心流程（今天要理解的唯一一件事）

```
你的问题 + 工具清单  ──第1次调用──▶  模型决定：调 get_weather(北京)
                                          ↓
                              你的代码真的去执行（模型不动手）
                                          ↓
工具结果塞回 messages ──第2次调用──▶  模型组织出最终回答
```

**模型全程不执行任何代码**，它只输出"我想调哪个函数、传什么参数"的 JSON。

## 3. 三个致命坑（原文踩过的，务必记住）

| 坑 | 后果 | 怎么避 |
|---|---|---|
| assistant 消息没加回 `messages` | 第 2 次调用时模型"失忆"，不知道自己说过要调工具 | `messages.append(msg)` |
| `tool_call_id` 和 `call.id` 对不上 | 结果关联不上，模型无法处理 | 用 `call.id` 原样回填 |
| 只取 `tool_calls[0]` | 模型一次要调 2 个工具时，第二个被吞掉 | 用 `for call in msg.tool_calls` |

## 6. 自测题

1. 模型返回 `tool_calls` 后，真正执行函数的是谁？
   <details><summary>答案</summary>是你的 Python 代码。模型只输出函数名和参数的 JSON，不碰任何外部系统。</details>

2. 为什么工具函数出错时要 `return "查询失败：xxx"` 而不是抛异常？   （链路不能中断，这就是返回字符串错误结果的目的)
   <details><summary>答案</summary>抛异常会让整个程序崩在半路；返回字符串则把错误当成"工具结果"回传给模型，模型能据此告诉用户"查询失败了"，链路不中断。</details>

3. 只改 `get_weather()` 函数体，为什么 tools 声明和调用闭环都不用动？
   <details><summary>答案</summary>模型只看 tools 里的 description，不关心函数内部是硬编码、HTTP 请求还是查数据库。</details>
